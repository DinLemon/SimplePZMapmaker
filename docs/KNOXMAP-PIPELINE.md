# KnoxMap adaptation: complete geographic world pipeline

Audit date: 2026-10-28. Workspace: `simplepzmapmaker-functionality-e254b9`; base HEAD at inspection: `66de4edc18d0c0aa5f4c53e4c439748a43f6a4a1`. The working tree already contains substantial uncommitted work and is being changed by other workers. Findings describe inspected files, including those changes, rather than just HEAD.

The required outcome is **choose area → terrain and infrastructure → usable furnished buildings → compile → install**, as one wizard within the existing editor. Street-grid detection and an Overture adapter are parts of this outcome, not a reduction of its scope. Every requested capability below remains tracked through an expected deliverable and its dependencies.

This is a read-only source/test inventory and integration design. Only this document was created. No application scripts, builds, tests, upstream scripts, server checks or game clients were executed for this audit; no commit, restart, mod activation, installation or real-profile write was performed. A cited test is inspected test evidence, **not a newly observed passing result** or proof of live gameplay.

## Existing execution map and proposed wizard

These are current code hooks unless explicitly called proposed. Paths below are repository-relative. `Core/`, `Services/`, `UI/` and `Tests/` in the capability inventory mean `src/SimplePZMapmaker.Core/`, `src/SimplePZMapmaker.Web/Services/`, `src/SimplePZMapmaker.Web/wwwroot/` and `tests/SimplePZMapmaker.Tests/` respectively.

### 1. Choose area and sources

- UI: `src/SimplePZMapmaker.Web/wwwroot/osm-world-import.js`, `OsmWorldImport.open`, `request`, `plan`, `start`, `apply`, `invalidate`. The current dialog already groups place/size/source selection and opens a completed import only after explicit application. Extend this same entry point with the remaining stages; keep the editor accessible for manual corrections.
- Layout: `src/SimplePZMapmaker.Web/Services/OsmWorldImportService.cs`, `OsmWorldImportRequest`, `Plan`; `src/SimplePZMapmaker.Web/Services/OsmWorldImportEndpoints.cs`, `POST /api/world/osm/plan`, `/jobs`, job status/cancel/result, and the parent's `/alignment` route.
- Data: `src/SimplePZMapmaker.Web/Services/OsmClient.Import.cs`, `FetchForImport`; `OsmSourceFiles.ImportAsync`, `SaveAsync`, `ReadAsync`, `Describe` in `Services/OsmSourceFiles.cs`; `Services/OsmSourceEndpoints.cs`, `/api/osm/sources` and `/api/osm/regions/plan`. The newly present `Services/OsmOvertureSource.cs:PrepareAsync` saves a distinct composed source through `/api/world/osm/supplement/overture`; `OsmWorldImport.addOverture` remembers that source for subsequent import. Use these immutable inputs, not another downloader.
- Proposed contract: persist a geographic selection mask, source IDs/hashes, source dates/attribution, seed, common frame and options as the wizard draft. The current request has a `GeoBounds`, rotation and warp, but no geographic polygon/circle/freehand mask.

### 2. Review geometry, terrain and infrastructure

- `src/SimplePZMapmaker.Core/GeographicProjection.cs` and `.Geometry.cs` own geographic-to-world/section conversion; `WorldGeoReference` in `Core/GeographicProjection.cs` owns the common frame. `GeographicWarpProposal.Create` and `GeographicWarpBuilder.Build` already provide a validated world deformation preview through `POST /api/geographic/warp/preview`.
- `src/SimplePZMapmaker.Core/GeographicImporter.cs`, `Import`, paints polygons/linear terrain and builds editable features; `LinearFeatureEditor.Rebuild`, `InfrastructureGeometry.Build` and `WorldInfrastructure.Build` compose native infrastructure. `Core/Automapping.cs`, `Preview`/`Apply`, and `Services/AutomappingEndpoints.cs`, `/api/automapping/preview`/`apply`, already provide reviewed street-detail placement.
- Proposed stage output: a section-addressable candidate with before/after geometry, roads/water/decks/props counts, omitted objects, estimated fields and conflicts. Explicit **Accept terrain and infrastructure** pins that candidate revision. Moving the selection, changing sources or changing projection invalidates downstream proposals.
- DEM hooks are `Services/WorldEndpoints.cs`, `/api/world/elevation/import` and `/download`, `TerrainElevationClient.Fetch`, and `Core/ElevationSurvey.cs`. DEM is currently survey/context data; it does not make native drivable slopes automatically.

### 3. Review furnished buildings and gameplay

- `GeographicImporter.Import` and `ImportWorldBuildings` in `Core/GeographicImporter.WorldBuildings.cs` generate local/shared source buildings. `ImportedBuildingGeometry.Apply` applies the actual outline/holes; `BuildingDesigner.Generate`, `Furnish`, `Validate`, `BuildingAccess.Validate`, `RoofGeometry` and `FurnitureCatalog` already serve the editor and exporter.
- `Core/GenerationStudio.cs`, `Preview`/`Provenance`, `Services/GenerationProposalStore.cs`, and `Services/GenerationStudioEndpoints.cs`, `/api/generation/studio/preview`, `/apply`, `/provenance`, are the current proposal/revision pattern for contextual generation. Reuse their protection and stale-preview checks. Current studio HTTP requests carry a map and optionally a complete world; a streamed wizard needs a lease/section adapter rather than posting all sections to these endpoints.
- Proposed stage output: footprint-specific generated layouts, height evidence, room/furniture/access/roof/light diagnostics, resource dependencies, occupancy heatmap and named-atlas preview. **Accept buildings and gameplay** retains generated vs measured provenance and permits corrections in the existing building/section editor.

### 4. Compile accepted revision

- Current entry: `Services/ExportJobEndpoints.cs`, `POST /api/world/workspaces/{id}/export/jobs` (or its selected-section route); `ExportJobStore.StartWorkspace`; `NativeExportService.Workspace`.
- Existing compiler: `Core/Export/NativeStreamedWorldExporter.cs`, `ExportAsync`; `Services/WorkspaceExportSource.cs`; `Core/Export/NativeMapExporter.cs`, `WriteCells`; `Core/Export/TileComposer*.cs`. `NativeExportMetadata.AddSection` accumulates bounded derived metadata and writes zones, atlas, spawnpoints, dependencies and attribution.
- Proposed stage output: one downloadable B42 mod archive with native cells, source index/sections, shared metadata and a manifest identifying the accepted source/frame/options/revision. Compile that immutable revision; show validation errors, progress and cancellation. Compilation alone never marks an install or client playtest successful.

### 5. Review and install compiled archive

- Current hooks: `Services/NativeExportService.cs`, `Options`, `Package`, `ModsDirectory`; `Core/Export/NativeModPackage.cs`, `Validate`, `Repack`, `Install`, `DefaultModsDirectory`. Completed job download supports `GET`/`POST`; `install=true` is accepted only on `POST`. Ordinary downloads do not install.
- Proposed final review: actual mod ID, map folder, destination, replacement of an existing tool-owned folder, dependencies and exact compiled revision. **Install** is a separate explicit action after compile. Reuse `Package`/`NativeModPackage.Install`; do not compile a different world silently on that click.
- Current installer stages extraction and refuses overwriting an unmarked existing mod folder. It does not establish a verified rollback after replacement failure. Do not promise transactional rollback without implementing/testing it.
- The deliverable includes activation/new-save/server instructions and an install receipt. The user's real profile remains untouched by this inventory. Later acceptance uses an isolated `PZMAP_MODS_DIR` and fresh test saves first.
