# Geographic sources and world import

The editor uses one source policy for a single map and a geographic world. Failed imports leave the current project in place. A world job produces a separate result; opening it is an explicit history operation.

## Regional downloads instead of a live Overpass dependency

**Automatic** first selects covering extracts from the official [Geofabrik catalogue](https://download.geofabrik.de/index-v1.json), downloads their PBFs and clips the requested area locally. The selection applies to every supported location; Smolensk has no automatic preference. Adjacent regions can cover a border selection, including polygon holes; an incomplete coverage plan fails explicitly. This does not promise that every country or subdivision has a suitably sized extract.

The original public Overpass failures remain provider availability failures: live checks on 2026-10-22 saw primary timeouts, an unavailable VK host, and Private.coffee timeout/HTTP 504 even for one node. Regional file downloads remove that service from the normal import path. A small saved source alone cannot fetch an unseen region; the regional path can.

## Sources

- **Automatic** uses Geofabrik first. If regional coverage or downloading is unavailable, it tries the online providers, then a previously downloaded compatible geographic snapshot with its original date disclosed. A completed PBF that fails local processing reports that processing error directly; it is not disguised as an online outage.
- **Geofabrik regional PBF only** uses the same covering regions without an Overpass fallback. **Check regional download** reports region names, expected download bytes, cache state, coverage and disk budgets before importing. The first file may be much larger than the selected map; subsequent imports reuse it for seven days.
- **Online Overpass** explicitly uses the online providers and their retry/cache logic. The read-only OSM map API remains a small-area backup; world downloads never use it for bulk requests.
- **Legacy Smolensk PBF** retains the explicit OSM France compatibility source. It is optional and is not selected as a geographic exception in Automatic.
- **Local file** accepts complete Overpass JSON, GeoJSON FeatureCollection/Feature, or a regional `.osm.pbf`, without OSM requests. Check that the file covers the selected area.

Official `latest` URLs currently redirect to dated snapshots. The downloader follows at most three verified redirects to the same origin, directory and region filename; arbitrary redirects remain rejected. Interrupted downloads retain partial bytes and resume only against a matching ETag/Last-Modified validator. Files are promoted only after PBF validation. A failed refresh keeps the previous validated source with a warning identifying its original date.

A `.part` can also be a complete transfer awaiting successful local extraction. Its metadata gains `Complete=true` only after EOF and length checks (or a matching HTTP 416 completion check). If extraction hits a geometry/output/index budget, the complete pending download is retained and can be reprocessed locally, without another network request, while fresh. It remains separate from validated `.osm.pbf` files until a successful read. Malformed framing and truncated PBF data are rejected rather than kept in an endless retry loop. The same distinction applies to an existing validated cache file that later encounters an output budget.

World status exposes `recovery`: `resume-download`, `retry-processing` or `retry-build`, plus `retainedRegionalSource` for a complete regional file whose local processing failed. The editor offers **Resume regional download**, **Retry downloaded source** or **Retry world build** accordingly. Build retries reuse the prepared source ID, including after a failed layout preflight; settings changes clear that recovery context. These failures do not direct the user to upload the large PBF through the separate 64 MiB manual-file limit. Progress and recovery actions stay in the visible dialog footer. A regional download/coverage failure retains a bounded regional reason even if all online fallbacks also fail; completing a transfer is reported separately from preparing selected JSON and assembling world sections.

Downloaded regional files live under `work/geodata-cache/regions/`, named by hashed catalogue identities relative to the active workspace. Limits are **8 GiB per PBF** and **16 GiB for the regional file cache**. Large PBF indexes use bounded buffers/memory-mapped windows and up to **16 GiB of temporary disk**, with free-space checks and cancellation cleanup. The entire region is not loaded into a managed node dictionary. The catalogue is limited to 32 MB and refreshed after seven days. Transfers have a **4-hour maximum** and a separate **5-minute inactivity deadline**, reset only when received bytes increase. Each PBF extraction and subsequent world assembly has its own **60-minute processing budget**. Source preparation has an overall 5-hour-5-minute ceiling. A healthy slow transfer no longer consumes the extraction or assembly deadline; cancellation still stops all phases.

Manual browser file uploads retain their separate **64 MiB PBF** limit. Single-map selected JSON is limited to 16,000,000 bytes, 30,000 features and 250,000 aggregate points; world selected JSON allows 64,000,000 bytes, 240,000 features and 1,000,000 aggregate points. These allowances are shared by PBF selection, saved-source inspection, world geometry aggregation, shared-building restoration and transfer checking. Per-object structural limits, bounded index retention and per-section core-import limits remain in force. Large regional relations are processed in a separate pass after the way index is complete: unrelated relations are released immediately, while selected geometry and one transient relation still share the 128 MiB retention cap. Cancellation and failure remove scratch indexes. The manual PBF path normalizes to at most 16 MB. Individual map and shared-metadata budgets still apply; bigger downloads do not remove them. Missing/incomplete relations are reported, not filled speculatively.

**Download saved source JSON** exports selected geographic data, not the generated project. Keep it outside the cache for durable offline use. At most 32 prepared source snapshots fit a separate 256 MB budget; old snapshots can expire. Sources are checked against their prepared bounds. A changed selection re-prepares a manual source. User-uploaded custom GeoJSON is never silently chosen as an online backup.

## World workflow

The geographic selection describes the **whole world area**. Section size describes **one map** in its shared grid. At 1 metre per tile, a 6 by 6 km selection with 1,024-tile sections produces 36 linked maps, padded to 6,144 by 6,144 tiles. Every section keeps the same projection, scale and origin; buildings and fences crossing a seam belong to shared world geometry. This is a selected part of Moscow, not the whole city or oblast.

Results exceeding the 128 MiB portable-world JSON budget are saved as a section workspace: a small common index, shared geometry metadata and independently stored maps. **Browse imported sections** opens its section picker without replacing the current project or downloading terrain. **Open only this section** loads one map with the shared context it needs; saved-world native export already reads sections individually. The picker shows total stored section/shared-plan bytes and disables **Load complete world** above the 128 MiB compatibility budget; use isolated editing or saved-world export for larger workspaces. Small results retain **Open imported world** and its one-step world undo. The source and assembly stage still has the bounded selection below and currently holds the assembled world on the server; this does not claim province-wide streaming generation.

1. Open **World from OpenStreetMap**, either from world tools or the single-map import dialog.
2. **Choose a place:** search for a city/address. **Enter centre coordinates** is available for precise locations. The current centre is always shown.
3. **Choose how much to import:** use Block (0.5 km), Neighbourhood (1 km), District (2 km) or Town (4 km), or enter a custom width/height. These are square geographic extents, not settlement generation strategies. Give the world a name and keep the recommended 1 metre per tile to preserve house dimensions.
4. **Your world layout** updates immediately without downloading: shading is the geographic selection, squares are joined editing sections and unshaded margins are padding. Rotation is included. Section size, exact bounds, cell origin, rotation and seed are under **Advanced layout settings**. Invalid bounds, coordinate origins or import budgets disable import before a network download.
5. **Choose where to get the data:** keep Automatic, or choose **Saved JSON or PBF · offline**. **Check download size** shows the initial regional file cost; **Check import** also validates the world layout on the server. Detailed source metadata and file/cache limits remain under **Source details and file limits**. A small selected area may still need a large initial region file.
6. **Download and build world** rechecks the settings and submits a background job. Follow its source/date and section progress; cancel or close/reopen the dialog without replacing the open world. The saved source remains downloadable if later composition fails.
7. For a large result, **Browse imported sections**, then choose a map and **Open only this section**. Browsing preserves the current project and edits. For a small result, **Open imported world** opens only a complete result. Changes made after the job started are absent from that result; use world undo to recover the previous state. Reopening import for a complete loaded geographic world enables **Refresh this world and keep manual edits**: its exact bounds, scale, rotation, origins, section size and area presets are locked until preservation is turned off.

One import supports at most 0.08° latitude and 0.12° longitude, 128 sections and 768 native cells under the separate assembly budget. The world format's larger 8,192-cell limit does not remove this import budget. Each stored section may be up to 128 MiB; common authored metadata is limited to 128 MiB (it includes full floor plans for buildings crossing seams), while the index is limited to 1 MiB. Their aggregate is not limited to one portable JSON file. Empty padded sections remain part of the shared world grid, including rotated selections.

## API

- `POST /api/osm/sources`: `{ name, bounds, json }` or `{ name, bounds, pbfBase64 }`. Returns source metadata and an opaque ID. Names are labels, never filesystem paths.
- `GET /api/osm/sources/{id}`: source metadata.
- `GET /api/osm/sources/{id}/download`: read-only normalized geographic JSON download.
- `POST /api/osm/regions/plan`: raw `{ south, north, west, east }` bounds; returns complete region coverage and download/cache estimates.
- `POST /api/import/osm/stream`: the map request below, with newline-delimited progress and a final result. The client applies only a complete terminal result. Aborting the request cancels download/index/compose; a partial result never replaces the map.
- `POST /api/import/osm`: the existing map request plus `sourceMode` (`auto`, `global`, `overpass`, `regional`, `file`) and optional `sourceId`. The response includes `sourceId`; legacy `useRegionalExtract` remains supported.
- World plan/job requests accept the same mode and ID. Job status exposes `sourceId` as soon as the source is available, before composition completes.
- A completed World job reports `resultKind: "world"` for a portable JSON result, or `resultKind: "sections"` and `workspaceId` for a saved section workspace. `/api/world/osm/jobs/{id}/result` returns the corresponding `.pzworld.json` or `.pzworld.index.json`; an index refers to application-managed section files and is not a standalone portable world. Workspace manifests, individual section reads and saved-world native exports use the existing `/api/world/workspaces/{workspaceId}` endpoints. Listing/browsing is read-only and cannot replace the active project.

All writes use the existing local-origin JSON request gate. Failed, cancelled, malformed and oversized downloads cannot replace the validated regional cache or current map. Saved-source IDs and bounds are validated before filesystem access; complete source writes are atomic.

## Verification

Network-independent C# tests cover provider refusals, automatic regional selection, corrupt/stale caches, source provenance, offline JSON/PBF, source bounds, cancellation, geometry filtering, seam buildings and complete-only world results. JavaScript tests cover selection, dimensions, source uploads and limits. Browser checks use isolated pages and fixtures; the user's open map is not changed.

World result tests force a small aggregate output budget to verify section fallback without allocating a 128 MiB test file. They retain exact section coordinates and common georeferencing, reject invalid worlds and conflicting workspace IDs, and cancel during section writes to verify cleanup. Publication of the immutable-section index is the completion point: job cleanup cannot remove a saved workspace, and there is no cancellable second result copy after publication.

`node scripts/verify-osm-linked-world-live.mjs` verifies a separately started cached 6 km Moscow job from `work/moscow-fixed-job.json`: 36 adjacent sections, 576 nonoverlapping cells, output larger than 128 MiB, sampled section/shared context reads, then actual editor index browsing and explicit single-section opening in an isolated Chrome context. It requires the corresponding saved Moscow source/cache; it never starts a download or changes the user's browser tab. Evidence is written under ignored `work/moscow-linked-world/`.

`python scripts/verify-osm-resilience-api.py` checks a real regional map, downloads and reimports its source, validates the offline map, and assembles a four-section offline world. Set `PZMAP_TEST_URL` to an editor using an isolated workspace with its regional cache. Evidence is written under ignored `work/osm-resilience-api/`.

`python scripts/verify-global-geodata.py --cities monaco berlin tokyo` exercises actual official regional sources, large PBF reading, streamed map composition and validation in an isolated server workspace. Add `--world` to assemble four adjacent sections from each selected area; `--plan-only` checks catalogue selection/download estimates without downloading files. Evidence is written under ignored `work/global-geodata-live/`. `node scripts/verify-osm-import-frontend.mjs` exercises the actual source/dialog modules in isolated Chrome fixtures, including truncated streams, cancellation, stale results and download planning.
